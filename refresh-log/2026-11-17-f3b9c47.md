Upstream subject: Clarify local hostname blocking on shared IP addresses (#26626)

**Decision: material.** Rule applied: material 5.

The commit adds a new subsection, 'Hostname blocking limitations', to content/manuals/ai/governance/local/network-rules.md, directly after the 'Allow or block a destination' examples. It also adds a paragraph to the reference page saying that, in local sandboxes, a denied host can still be reached when it shares an IP address with an allowed host. Three cases are named: connections the proxy doesn't decrypt, later requests on a cleartext connection sent through CONNECT or without HTTP_PROXY, and connections that name no host. This limits claim L1-S3-3 ('Denying a host blocks that destination, even when a group or a kit allows it'), which is now false in the shared-IP case, so it is a new edge case whose home is Lesson 1 s4. L1-S1-1 and L2-S4-1 are not listed because rule precedence and the check result for the attributed hostname are unchanged. A reviewer should still confirm that the Lesson 1 assess model reply, which is derived partly from L1-S3-3, doesn't promise that a deny always makes a host unreachable.
