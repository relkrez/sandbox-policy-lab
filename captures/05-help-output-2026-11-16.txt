  Description:
    Manage persistent access policies for sandboxes.

    Policies contain rules that control what sandboxes can access. Local rules
    can apply globally across all sandboxes or be scoped to one sandbox. Use
    subcommands to allow, deny, list, or remove rules.

    Network rules match the hostname a connection names, such as its TLS SNI or
    HTTP Host. A denied host that shares an address with an allowed host can
    still be reached in three cases. First, on connections the proxy does not
    decrypt, the HTTP Host or :authority inside the encrypted stream is not
    checked. Second, on cleartext HTTP sent through a CONNECT tunnel or without
    HTTP_PROXY, only the first request on each connection has its Host checked.
    Third, a connection that names no host is allowed when any hostname the
    sandbox resolved to that address is allowed, even if another of those
    hostnames is denied.

  Usage:
    sbx policy COMMAND

  Available Commands:
    allow       Add an allow rule for sandboxes
    approval    Review and respond to pending approvals
    check       Check whether policy allows an access request
    deny        Add a deny rule for sandboxes
    init        Initialize the global network policy
    inspect     Show policy or rule details
    log         Show sandbox policy logs
    ls          List sandbox policies
    profile     Manage policy profiles
    refresh     Force an immediate policy refresh
    reset       Reset policies to defaults
    rm          Remove a policy rule

  Flags:
    -h, --help   help for policy

  Global Flags:
        --cloud      Dispatch to Docker Cloud Sandboxes API instead of local sandboxd (supported by a growing set of verbs — run 'sbx --cloud --help' for the current list)
    -D, --debug      Enable debug logging
        --no-input   Never prompt; commands that need an answer fail with the command to run instead

  Use "sbx policy COMMAND --help" for more information about a command.

  Description:
    Add a rule that blocks sandboxes from accessing specified resources.

    Deny rules take precedence over allow rules for the same hostname or CIDR. A
    direct connection to an allowed hostname is also checked against CIDR rules for
    its resolved IP address, and a deny on either takes precedence. Connections
    through an upstream proxy that resolves the hostname are checked by hostname
    only.

    Without --cloud, a rule is refused, and nothing is added, when the same scope
    already holds the opposite decision for the same resource on any of the same
    protocols (for HTTP rules, the same methods, path, and query constraints).
    Remove the existing rule with "sbx policy rm network --id RULE_ID" first, adding
    --sandbox SANDBOX if the rule is sandbox-scoped. Rules in different scopes, such
    as a global allow and a sandbox-scoped deny, can coexist, and the deny rule
    takes precedence. Rules from your organization's policy never cause this
    refusal. With --cloud, the new rule replaces the opposite rule in the same scope
    instead.

  Usage:
    sbx policy deny COMMAND

  Available Commands:
    network     Deny network access to specified hosts

  Flags:
    -h, --help   help for deny
