Case study

A self-updating sandbox policy course

By David Zerkler, Helm Vision Services Inc. · November 2026

Course: relkrez.github.io/sandbox-policy-lab

Workflow and source: github.com/relkrez/sandbox-policy-lab

Problem

Teams adopting Docker Sandboxes need training that keeps pace with the product. Docker's public training teaches developers to run sandboxes; admins learn in live onboarding. Nothing self-paced teaches admins and security reviewers to decide, change, and verify a sandbox's network policy.

Solution Summary

With Claude, I built an interactive course on hardening a sandbox policy, and a GitHub workflow that keeps the course current. No AI draft reaches learners until a subject-matter expert (SME) approves it.

Course

https://relkrez.github.io/sandbox-policy-lab/index.html

Two 30-minute lessons. Lesson 1 teaches how to decide what an agent should reach. Lesson 2 is a lab: learners change and verify the policy in their own terminal, predicting each result first.

Workflow

https://github.com/relkrez/sandbox-policy-lab

Each night, the workflow checks the Docker documentation pages the course draws on. If a change affects what the course teaches, Claude drafts an update and the workflow emails the SME a pull request with the reasoning, a preview, and a checklist. The SME merges, edits, or rejects.

In its first week, it caught a real change: a blocked host can sometimes be reached through an IP address shared with an allowed host. I approved its draft with one edit.

Needs Analysis

Without customer data, I based learner profiles on the job description and my experience, to be checked with Professional Services and TAMs. Rating each group's skills against the tasks a sandbox policy demands produced four groups:

Group Who Needs Course
1. Operators Admins and DevOps (low, medium), IT (medium, high) Judgment on what to allow This sample
2. Judges Security (low, medium) Hands-on CLI practice This sample
3. Experts Admins, security, DevOps (high) How Docker's rules differ; automation Advanced (not built)
4. Newcomers IT (low), non-developer teams Recognize a block and request access Prerequisite (not built)

Groups 1 and 2 mirror each other: one can operate but not judge, the other the reverse. One course serves both, so I built it first.

Course objectives

Lesson 1, Decide what a sandbox can reach. Learners can:

  • Explain how a sandbox network rule prevents unwanted access.

  • Describe the rules in local-policy, in default-deny-all, and in the Claude Code kit policy.

  • Evaluate the consequences of adding or removing a rule.

Lesson 2, Change and verify a sandbox policy. Learners can:

  • Find a command's syntax and flags with --help.

  • Inspect the policies and rules in force on a machine.

  • Modify the local policy by removing a rule group, allowing a host, and denying a host.

  • Verify each change, and identify which rule decided the result.

Cost and measurement

  • Build, at steady state: 25 to 30 hours for this course, including SME review.

  • Workflow: 8 hours to set up, then 1 to 2 hours of SME review a month.

  • AI credits: a Claude subscription, plus under $10 a month for the workflow.

  • Measures: check-script pass rate, time to a customer's first hardened policy, and policy support tickets.
