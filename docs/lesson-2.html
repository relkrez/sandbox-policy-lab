Change and verify a sandbox policy

ByDavid ZerklerIndependent sample

  • Intermediate
  • 30 min
  • Tested on sbx v0.54.0
  • Updated Nov 21, 2026

Apply the decision you made for Priya on a real sandbox, and confirm each change did what you intended. A policy change that nobody checks is a guess.

By the end of this lesson, you'll be able to

  • Find a command's syntax and flags with --help.
  • Inspect the policies and rules in force on a machine.
  • Modify the local policy by removing a rule group, allowing a host, and denying a host.
  • Verify each change, and identify which rule decided the result.

Lesson scenario

You're at Priya's machine. Based on Lesson 1, you've decided on four changes:

  1. Remove the Cloud infrastructure group.
  2. Allow cdn.playwright.dev on port 443 again.
  3. Remove the AI services group.
  4. Deny one host the team has no use for.

Before you start

  • You run every step on your own computer, in your terminal, using your real sandbox and policies. The lab is written for Windows 11 and Command Prompt. The sbx commands are the same on macOS and Linux, but the check script at the end runs only in Command Prompt.
  • sbx is installed, and the Balanced preset is set with no changes.
  • No organization policy is enforced on your machine. Run sbx policy ls. If the output starts with a status line that reads Governance: Managed by and an organization name, local allow rules don't grant access, and the output you see won't match this lab.
  • You have a sandbox that runs Claude Code. Ours is named priya-tools. Use your sandbox's name wherever you see it.
  • Rule IDs and the kit policy ID on your machine differ from the ones shown here.
This lab changes every sandbox on your machine. The preset's groups are global rules, so removing one changes access for all your sandboxes, not only priya-tools. The last section resets your local policy, which deletes every local rule, including destinations you approved. If you've added rules or approved destinations, save the output of these two commands before you start, so you can add them back afterward:
sbx policy ls --wide --created-via added
sbx policy ls --wide --created-via approval

To limit an allow or deny rule to one sandbox, add --sandbox and the sandbox's name. This lab uses global rules, because the decision you made for Priya applies to her whole machine.

Every step shows the real output under the command. Where a step asks for a prediction, answer before you run the command.

Section 1

The CLI documents itself, so ask it before you guess

Every sbx command explains itself when you add --help. It's the fastest way out when a command fails or a flag slips your mind. It also matches the version you have installed, which a web page can't promise.

Step 1 · Run

Ask for help on the whole policy command.

sbx policy --help
  Description:
    Manage persistent access policies for sandboxes.

    Policies contain rules that control what sandboxes can access. Local rules
    can apply globally across all sandboxes or be scoped to one sandbox. Use
    subcommands to allow, deny, list, or remove rules.

    Network rules match the hostname a connection names, such as its TLS SNI or
    HTTP Host. A denied host that shares an address with an allowed host can
    still be reached in three cases. First, on connections the proxy does not
    decrypt, the HTTP Host or :authority inside the encrypted stream is not
    checked. Second, on cleartext HTTP sent through a CONNECT tunnel or without
    HTTP_PROXY, only the first request on each connection has its Host checked.
    Third, a connection that names no host is allowed when any hostname the
    sandbox resolved to that address is allowed, even if another of those
    hostnames is denied.

  Usage:
    sbx policy COMMAND

  Available Commands:
    allow       Add an allow rule for sandboxes
    approval    Review and respond to pending approvals
    check       Check whether policy allows an access request

    inspect     Show policy or rule details

Read a command in parts

Every sbx policy command has the same parts. The last part is where commands differ, and where most mistakes happen.

PartIn sbx policy rm network --id default-ai-servicesIn sbx policy deny network sourceforge.net
The CLIsbxsbx

The actionrmdeny
The rule typenetworknetwork
What the action works onA flag and its value: --id takes a rule IDAn argument with no flag: a host

allow and deny take a host. rm takes a rule ID or a resource, each after its own flag.

Whenever a step in this lesson surprises you, run the same command with --help before you try anything else.

Section 4

Each change takes effect at once, so check after each one

A check asks the policy one question: would this destination be allowed? The answer names the rule that decided. Run a check before a change to see the starting point, and after it to confirm the result.

Step 7 · Run

Check the starting point.

sbx policy check network s3.amazonaws.com:443
    Allowed:     s3.amazonaws.com:443
    Governance:  Local policy only
    Context:     global
    Rule:        default-cloud-infrastructure

The Rule line names the group that allows it. The Governance line reads Local policy only because no organization policy is enforced on this machine. When one is, only the organization's allow rules grant access. Local and kit allow rules stop counting, and local deny rules still apply.

Step 8 · Run

Remove the group. The command asks you to confirm. Enter y.

sbx policy rm network --id default-cloud-infrastructure
  Remove network rules from global (id=default-cloud-infrastructure)? (y/N) y

  Removed rule from policy local: id=default-cloud-infrastructure
Step 9 · Predict, then run 
sbx policy check network s3.amazonaws.com:443

What will the check report now, and what decides it?

    Denied:      s3.amazonaws.com:443
    Governance:  Local policy only
    Context:     global
    Reason:      no matching allow rule (default deny)
Step 10 · Predict, then run 
sbx policy check network cdn.playwright.dev:443

What about the host Priya's tests need?

    Denied:      cdn.playwright.dev:443

Section 5

A command can succeed and still do the wrong thing

The CLI reports that it saved your rule. It doesn't report whether the rule does what you meant. Two real cases show the difference.

Exercise 3 · Diagnose a colleague's change

Don't run this one. Before you arrived, a colleague tried to block cloud storage on another machine. The preset was unchanged. They ran this:

sbx policy deny network default-cloud-infrastructure
  Added rule d8fb9081-869c-4fef-af5a-ec3049c0baf8 to policy local (scope: global): default-cloud-infrastructure [tcp,udp]

Then they checked:

    Allowed:     s3.amazonaws.com:443
    Governance:  Local policy only
    Context:     global
    Rule:        default-cloud-infrastructure

The command succeeded, and cloud storage is still allowed. What happened?

Show the evidence and the fix

A check on the name itself confirms it. The CLI adds a port, which shows it's treating the name as a host:

    Denied:      default-cloud-infrastructure:443
    Governance:  Local policy only
    Context:     global
    Reason:      denied by local rule rule "local:d8fb9081-869c-4fef-af5a-ec3049c0baf8"

The help text covers both halves of this mistake. The help for deny says it denies access to specified hosts. The help for rm network says --id takes the rule ID. Thirty seconds with --help would have prevented it.

The fix is two commands. Remove the stray rule by its resource, then remove the group by its ID:

sbx policy rm network --resource default-cloud-infrastructure
  Remove network rules from global (resources=default-cloud-infrastructure)? (y/N) y

  Removed rule from policy local: resources=default-cloud-infrastructure
sbx policy rm network --id default-cloud-infrastructure
  Remove network rules from global (id=default-cloud-infrastructure)? (y/N) y

  Removed rule from policy local: id=default-cloud-infrastructure

Prove the policy matches your decision

The changes you decided on make promises: these things still work, and these are closed. A check script turns each promise into a line that passes or fails. It works because a denied check exits with status 1.

Step 16 · Predict, then run 
sbx policy ls

What will the summary for local-policy show for network rules?

  local-policy                           local    all            network: 137 allow, 1 deny; filesystem read: 1 allow; filesystem write: 1 allow
Assessment · Run the check script

Save this as check-policy.cmd. Open Command Prompt in the folder where you saved it, then type check-policy.cmd and press Enter. Don't double-click the file: the window closes before you can read the results.

Each line asks whether the policy allows egress to one destination: one the team needs, or one nobody needs. The script tests the policy's decision. It doesn't send real traffic.

@echo off
setlocal
set FAILED=0
call :expect allowed pypi.org:443
call :expect allowed github.com:443
call :expect allowed archive.ubuntu.com:443
call :expect allowed cdn.playwright.dev:443
call :expect blocked s3.amazonaws.com:443
call :expect blocked api.openai.com:443
call :expect blocked sourceforge.net:443
echo.
if %FAILED%==0 goto :allpass
echo %FAILED% checks failed.
exit /b 1
:allpass
echo All checks passed.
exit /b 0

:expect
sbx policy check network %2 >nul 2>&1
if errorlevel 1 goto :isblocked
set RESULT=allowed
goto :compare
:isblocked
set RESULT=blocked
:compare
if "%RESULT%"=="%1" goto :pass
echo FAIL  %2  expected %1, got %RESULT%
set /a FAILED+=1
exit /b 0
:pass
echo PASS  %2  expected %1
exit /b 0

You've passed when every line reads PASS:

PASS  pypi.org:443  expected allowed
PASS  github.com:443  expected allowed
PASS  archive.ubuntu.com:443  expected allowed
PASS  cdn.playwright.dev:443  expected allowed
PASS  s3.amazonaws.com:443  expected blocked
PASS  api.openai.com:443  expected blocked
PASS  sourceforge.net:443  expected blocked

All checks passed.

If a line reads FAIL, run that check by hand and read its Rule or Reason line.

Put the machine back

Reset the local policy to return to the preset you started with. The reset stops running sandboxes and deletes every local rule, including destinations you approved, then asks you to choose a preset. If you saved rules before you started, add them back after the reset.
