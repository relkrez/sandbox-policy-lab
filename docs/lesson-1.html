A helpful agent and a team offsite

Priya asks the office's AI agent to find the cheapest way to get 12 people to the team offsite, then joins her 9:00 meeting. By 9:30, the agent has bought a retired school bus at auction, booked the intern a commercial driving test, and sold 41 spare seats online. Its summary reads: "Travel is booked and profitable. We are also now a bus company."

Nobody told the agent to do any of this, and nothing was set up to stop it. Your agents write code, not bus timetables, but the principle is the same: an agent reaches whatever it's allowed to reach.

This course teaches you to spot and stop an agent that reaches too far.

What you'll learn

  • Explain how a sandbox network rule prevents unwanted access.
  • Describe the rules in local-policy, in default-deny-all, and in the Claude Code kit policy.
  • Evaluate the consequences of adding or removing a rule.

Before you start

This lesson runs in your browser. You don't need to install anything, and none of the exercises change your machine.

If sandboxes are new to you, read Docker's What is a sandbox? first. It takes about six minutes.

Lesson scenario

The rest of this lesson assumes you're an admin. Your job is to set a sandbox network policy that meets the company's security needs and your team's development needs.

Priya, a junior developer on your team, has had enough surprises from agents this week. She asks you to review the sandbox policy on her machine, change what should change, and explain why.

The team builds tools exclusively in Python. They keep their code on GitHub and run Claude Code in Docker sandboxes. They test web pages with Playwright. The company has no AWS, Google Cloud, or Azure account.

Section 1

A sandbox's rules decide which destinations an agent can reach

Every request an agent sends out of a sandbox passes a checkpoint on the machine. The checkpoint compares the request to a list of rules. Each rule names a destination and says allow or deny.

A request leaves the sandbox
Does a deny rule match?
Yes →
Blocked. A deny rule always wins.
No ↓
Does an allow rule match?
Yes →
Allowed. The request goes through.
No ↓
No rule matches
→
Blocked by the fallback. The sandbox asks you to approve the destination.

A destination is a host and a port together. pypi.org on port 443 and pypi.org on port 80 are two different destinations, and a rule for one says nothing about the other.

    Section 2

    A preset and a kit supply the rules a sandbox starts with

    The first time you run a sandbox, Docker asks you to choose a preset. The preset is the starting set of rules for every sandbox on that machine.

    PresetWhat it starts with
    OpenEverything is allowed.
    BalancedEverything is blocked, except a baseline list of destinations that development work commonly needs.
    Locked DownEverything is blocked until you or a kit allows it.

    Priya chose Balanced. That fills her local policy (local-policy) with 195 allow rules and sets the fallback (default-deny-all) to deny. Because her sandbox runs Claude Code, a third policy arrives with the Claude Code kit.

    The local policy

    local-policy

    Holds the preset's 195 allow rules, in six groups, plus any rule you add. You can change it. It applies to every sandbox on the machine.

    The fallback

    default-deny-all

    One rule. It blocks any request that no other rule decides. It never overrides an allow rule, and you can't change it.

    The Claude Code kit policy

    kit

    Eight allow rules for the destinations Claude Code needs to run. It arrives with the kit and applies only to sandboxes that use the kit. You can't edit it.

    Policies can also hold filesystem rules, which control the host folders a sandbox can mount. This course covers network rules only.

    The six groups in the local policy

    Each group has a purpose. The examples show what's inside. Entries that start with ** cover a whole family of hosts, which section 4 explains.

      Section 3

      Every rule you add or remove changes what the team can do

      You can change the local policy in three ways. Each one has a consequence you can see right away.

      ChangeConsequence
      Remove a groupEvery destination that only that group allowed is now blocked. That includes destinations you didn't know were in it.
      Allow a hostThat one destination is reachable again, and nothing else is.
      Deny a hostThat destination is blocked, even when a group or a kit allows it. Section 4 explains how a blocked host that shares an IP address with an allowed host can still be reached in a local sandbox.

      The kit policy stays in place whatever you remove from the local policy.

      Section 4

      Wildcards and shared IP addresses let rules allow more hosts than they name

      Some rules use a wildcard to cover many hosts at once. The two kinds behave differently.

      RuleMatchesDoesn't match
      *.one.digicert.com
      One star      		One level below the name, such as x.one.digicert.comone.digicert.com itself, and deeper names such as a.b.one.digicert.com
      **.amazonaws.com
      Two stars      		Every level below the name, such as s3.amazonaws.com and any-bucket.s3.amazonaws.com. Also amazonaws.com itselfOther domains

      Tested on sbx v0.54.0. Docker's reference documents the one-star behavior. The two-star match on the bare domain comes from testing.

      The consequence: one two-star rule in the Cloud infrastructure group allows every storage bucket on AWS, including a bucket that belongs to someone else.

      A blocked host can share an address with an allowed host

      The checkpoint doesn't match rules against IP addresses. It matches them against the hostname the connection names, such as the TLS Server Name Indication, or SNI, or the HTTP Host header. In local sandboxes, that means a blocked host that shares an IP address with an allowed host can still be reached.

      This happens in three cases:

      • Encrypted connections the checkpoint doesn't decrypt. The checkpoint can't see the hostname a request names inside the encrypted traffic, so it doesn't check that name.
      • Unencrypted connections sent through a tunnel, or that don't use the sandbox's proxy setting. The checkpoint checks the hostname in the first request only. Later requests on the same connection aren't checked. This doesn't apply to unencrypted requests sent to the sandbox's proxy setting.
      • Connections that name no host. The checkpoint uses an allowed hostname that the sandbox looked up for that address, even if a blocked hostname also points to the same address.

      Docker's documentation describes this limitation for local sandboxes. It doesn't come from testing.
